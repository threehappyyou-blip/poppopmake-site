JSON, Base64, UUID & Color

Four small utilities every dev reaches for constantly, without the ad-choked pages most of these tools live on.

Worked example

The box loads with a sample object already in it — {"name":"PopPopMake","categories":["Documents","Money","Career","Business","Writing","Everyday"],"free":true,"count":6} — and the formatter runs once automatically as the page loads, so the Result box already shows it pretty-printed at 2-space indent: the outer object, the six-item categories array with one string per line, then free and count each on their own line. Switch the dropdown to "Minify (no spaces)" and click Format again, and the same object comes back as a single compact line instead, because Minify doesn't strip whitespace from your original text — it re-parses it and re-serializes it with no indentation argument at all.

Frequently asked questions

What happens if I paste something that isn't valid JSON?

The status line shows "Not valid JSON:" followed by whatever message the browser's own JSON.parse throws, and the Result box is cleared rather than showing a partial guess. That message comes from the JavaScript engine itself, not a custom parser built for this tool, so its specificity varies — a stray trailing comma, for example, can report a line and column, while truncated input just reports "Unexpected end of JSON input" with no position at all. Exact wording can differ between browsers, since each has its own JSON parser.

Why do large numbers or trailing decimals sometimes look different after formatting?

Formatting works by parsing your text into a real JavaScript value with JSON.parse and then re-serializing that value with JSON.stringify, rather than reformatting your original characters in place. That means a number typed as 1.50 comes back as 1.5 — the trailing zero isn't preserved once it becomes a JavaScript number — and an integer larger than JavaScript can represent exactly (above 2^53) can shift to a nearby value. This is a property of round-tripping through JSON.parse/JSON.stringify, not a bug specific to this formatter.

What does "Minify" actually do?

It reparses your JSON and re-serializes it with no indentation argument, which renders as a single compact line. Because it goes through a real parse step first, it also validates your input along the way and rejects anything that isn't strictly valid JSON — including JSON with comments or trailing commas, neither of which the JSON format allows.

I changed the indent dropdown but the output didn't change — why?

The dropdown only takes effect the next time you click Format — changing it doesn't re-run formatting by itself. If you've already formatted something, pick the new indent option and click Format again to see it applied.

Does this tool send my JSON anywhere?

No. Parsing and formatting both happen with the browser's built-in JSON.parse/JSON.stringify — nothing you paste here is transmitted to or stored on a server.

Worked example

The box loads with the sample text Hello, PopPopMake! 안녕하세요 🎉, mixing plain ASCII, Korean, and an emoji on purpose. Clicking Encode writes SGVsbG8sIFBvcFBvcE1ha2UhIOyViOuFle2VmOyEuOyalCDwn46J into the Base64 box below; clicking Decode right after reads that same box and writes the exact original text back above, Korean characters and emoji intact. That round trip works because encoding first converts your text to UTF-8 bytes with TextEncoder before btoa ever sees it, and decoding reverses that with atob and TextDecoder.

Frequently asked questions

Does this correctly handle Korean text, emoji, or other non-English characters?

Yes — and that's by design, not accident. Rather than calling btoa/atob directly on your text, it first runs the text through TextEncoder to get its UTF-8 bytes and encodes those, then reverses the same path with TextDecoder on decode. A plain, unwrapped btoa() call throws an error on any character outside Latin-1, which includes Korean text and most emoji — this extra step is what makes round-tripping that text possible at all.

What happens if I click Decode on text that isn't valid Base64?

The status line shows "Not valid Base64:" followed by the real error the browser's atob throws — typically "Invalid character" — and the text box above is left untouched. Characters outside the standard Base64 alphabet, or incorrect padding, are the usual cause.

Will Base64 produced by another tool or programming language decode correctly here?

Standard Base64 (the alphabet using +, /, and = padding) will. URL-safe Base64 (using - and _ instead) will not — decoding here goes through the browser's standard atob, which rejects those characters rather than treating them as equivalents.

Does it matter if the Base64 text has extra line breaks or spaces, like from a copy-paste?

Not much — stray whitespace inside or around the Base64 text is skipped when decoding, and this tool also trims the box before decoding. What it won't tolerate is a non-whitespace character that isn't part of the Base64 alphabet.

Does encoding or decoding here send my text anywhere?

No. Both directions run entirely in your browser using built-in TextEncoder/TextDecoder and btoa/atob — nothing you type or paste is sent to a server.

Worked example

The page generates one UUID automatically on load, and every click of "Generate new UUID" produces a fresh one — there's no fixed seed, so the exact value differs each time, but the shape never does: four hyphen-separated groups like dd162d6f-97d0-4d30-af3f-cc37d63e53f4, where the third group always starts with 4 (marking it as version 4) and the fourth group always starts with 8, 9, a, or b (the variant bits). Set "Generate multiple" to a number between 1 and 100 and click "Generate list" to get that many at once, built the same way.

Frequently asked questions

Which version of UUID does this generate, and how random is it really?

Version 4 (random) UUIDs. When the browser supports it, generation calls the Web Crypto API's crypto.randomUUID() directly, which draws from a cryptographically strong random source. Only in browsers old enough to lack that method does it fall back to a Math.random()-based template that fills in the same version and variant bits by hand — Math.random() isn't cryptographically secure, so that fallback path shouldn't be relied on for anything security-sensitive, like tokens or secrets.

Could this ever generate the same UUID twice?

There's no active check against it — this tool doesn't remember what it generated before, in this session or any other. A collision isn't prevented, just made astronomically unlikely by the sheer number of random bits (122 of them) a v4 UUID has to work with.

What's the difference between "Generate new UUID" and "Generate list"?

"Generate new UUID" replaces the single value at the top. "Generate list" produces a separate batch below it — anywhere from 1 to 100 at once, clamped to that range even if you type a larger number — without touching the single UUID above.

Can I copy just one UUID out of a generated list?

Not with a dedicated button — only the single UUID at the top has a Copy button next to it. For one out of a batch, select and copy its text directly, or regenerate it alone using "Generate new UUID" at the top instead.

Does generating UUIDs here send anything to a server?

No. Every UUID, single or batch, is generated locally with crypto.randomUUID() or the Math.random() fallback — there's no input to send in the first place, and nothing is transmitted anywhere.

Worked example

The box loads with #0D7A7C already filled in, and conversion runs immediately and again on every keystroke after that — there's no button to click. That starting value converts to rgb(13, 122, 124) and hsl(181, 81%, 27%), and the HEX output re-renders as lowercase (#0d7a7c) regardless of how you typed it, since it's rebuilt from the calculated values rather than echoing your input back. Three-digit shorthand works too — typing #0d7 expands each digit (0→00, d→dd, 7→77) into rgb(0, 221, 119).

Frequently asked questions

Can I type an RGB or HSL value and convert it the other way?

No — HEX is the only editable field here. RGB and HSL are read-only outputs calculated from whatever's in the HEX box, so conversion only runs in one direction.

What hue does a pure gray, like #808080, get?

0. Hue is mathematically undefined for a color with no saturation — where red, green, and blue are all equal — and this tool explicitly reports 0 in that case rather than leaving it blank.

What happens if I type an incomplete or invalid hex code?

The status line shows "Enter a valid hex color, like #0D7A7C or #0d7," and the swatch and output fields simply stop updating, keeping whatever they last showed. Only exactly 3 or 6 hex digits (with or without a leading #) are accepted — any other length is rejected outright.

Does the HEX output preserve the uppercase or lowercase I typed?

No. The HEX output is always lowercase no matter how you typed it, because it's rebuilt from the calculated RGB values rather than reusing your original characters.

Does converting a color here send it anywhere?

No. The hex-to-RGB-to-HSL math runs entirely in your browser — nothing you type into this tool leaves your machine.

Worked example

The box loads with hello world & special=chars?. Clicking Encode writes hello%20world%20%26%20special%3Dchars%3F into the Result box — the space becomes %20 rather than +, and &, =, and ? are each percent-escaped, since encodeURIComponent treats them as reserved characters that need escaping inside a single value. Clicking Decode right after reads that same Result box and writes the original text back above, unchanged.

Frequently asked questions

Why does a space become %20 here instead of a +?

Because this uses encodeURIComponent, which always escapes a space as %20. The +-for-space convention belongs to form submissions (application/x-www-form-urlencoded), not to encodeURIComponent — if you specifically need that form-encoding behavior, this tool's output won't match it.

Can I encode a whole URL with this, like https://example.com/search?q=a b?

You can, but the result won't be a usable URL — the status message after encoding says as much: this is meant for text or query values, not full URLs. encodeURIComponent escapes every reserved character it sees, including :, /, ?, and &, so encoding a whole URL would also escape the :// and path separators you need to keep intact.

What happens if I click Decode on text that isn't valid percent-encoding?

The status line shows "Not valid percent-encoded text:" followed by the native error — typically "URI malformed" — and the text box above is left untouched. A % not followed by two valid hex digits is the usual cause.

Does this use the older escape()/unescape() functions instead?

No — it's encodeURIComponent/decodeURIComponent. That matters most for non-ASCII text: the deprecated escape() leaves characters like + unescaped and encodes non-ASCII text as a non-standard %uXXXX form, while encodeURIComponent percent-encodes the actual UTF-8 bytes, which is what URLs and query strings actually expect.

Does encoding or decoding here send my text anywhere?

No. Both directions run locally using the browser's built-in encodeURIComponent/decodeURIComponent — nothing you type or paste is sent to a server.

Frequently asked questions

What fields does this actually generate — is there lorem ipsum or other free text?

No lorem ipsum. Each row has exactly five fields — first name, last name, email, phone, and address — assembled from fixed lists of realistic-looking US names, street names, and city/state pairs rather than generated free text. There's no company name, date of birth, username, or any field type beyond those five.

Are the generated addresses and phone numbers real or deliverable?

No. City and state are pulled together as a matched pair from a fixed list of ten real combinations, but the street number, the street-name-and-type pairing, and the 5-digit number standing in for a ZIP code are all independently random — so the result looks like a plausible US address without being validated against any real address or area-code database.

If I generate a lot of rows, will names repeat?

Past a certain point, they have to. Each field is picked independently from a fixed list — 40 first names, 30 last names, 10 city/state pairs — with no check against rows already produced in the same batch. Request more than 40 rows (the maximum is 200) and at least one first name is guaranteed to repeat somewhere in the results, simply because there aren't enough unique names to go around; past 30 rows, the same is true for last names.

Do "Copy as CSV" and "Copy as JSON" match the table exactly?

The data is identical, but the shape differs. The CSV export uses the same human-readable headers as the table — First Name, Last Name, Email, Phone, Address, written plain on the header line — with each data value below it quoted and any internal quotes doubled, while the JSON export uses the underlying camelCase field names (firstName, lastName, email, phone, address) instead, pretty-printed with 2-space indentation.

Does generating or copying this data send it anywhere?

No. Every row is generated locally using the Web Crypto API's crypto.getRandomValues, and copying the result to your clipboard doesn't involve a network request — nothing here is sent to or stored on a server.

Everything on this page runs in your browser — nothing you paste or generate is sent anywhere, which matters most for JSON that might contain real data. See how to check that yourself.
